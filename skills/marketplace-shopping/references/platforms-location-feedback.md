# Platforms browser access location and feedback

Read this reference when choosing marketplaces, checking browser sign-in, changing location or applying listing feedback. Read state first and use the latest revision for every write.

## Marketplace execution

Each search has `marketplaces`; older searches without this field use only Facebook Marketplace. Settings `platforms` can disable a platform or override its browser. Read `list_goodfinds_marketplace_capabilities` for current collection routes and eBay credential availability. Build queries from the brief, saved research queries, candidate models and broader feature terms. Research candidates remain expandable, not a hard whitelist.

Facebook uses the established host browser workflow. `search_goodfinds_ebay` returns one page of fixed-price [Browse evidence](https://developer.ebay.com/api-docs/buy/api-browse.html) in eBay order; use `get_goodfinds_ebay_listing` for details. API credentials belong in the server environment, never chat or settings. Inspect images, verify attributes, costs and availability, then import evidence. A returned API page is not a completed inspection or a complete search.

Vinted, Gumtree, Auto Trader and Craigslist currently offer navigation and normalized imports. Use user-provided evidence or an established authorised collection route. [Vinted Pro inventory access](https://pro-docs.svc.vinted.com/) is not a general buyer search API; [Gumtree's terms](https://www.gumtree.com/termsofuse) require permission for automated collection, and [Auto Trader Connect](https://help.autotrader.co.uk/hc/en-gb/articles/21791620456221-Integration-Fundamentals) needs credentials, authorised dealer access and production checks. Recheck applicable regional terms when establishing a collector. Report unavailable routes and partial coverage instead of pretending each selected marketplace was checked.

Keep each platform's identity, costs, currency, price period and seller evidence distinct. Unsupported seller signals remain unknown, rather than turning Facebook-specific friend counts into other platforms' requirements. Fixed-price asking prices, auction bids and finance quotations are different price kinds. See [platform interpretation](observations.md#platform-interpretation) when recording date, price or visibility evidence.

## Check access and sign-in

Use the host's supported browser capability inventory and permission flow. Record an observed capability using `report_goodfinds_browser_access`, supplying the current state's `access_context` as `context_id`, actual host/profile identity and evidence. Report available, not_connected, denied, unavailable or unknown accurately. Missing tools do not establish an OS permission denial. Chrome extension access can supply browser control without broad native computer use.

Verify website sign-in within that browser profile and record it using `report_goodfinds_marketplace_session`. Public access does not prove sign-in. In-app and device-browser logins are separate. Browser preferences can be saved before connecting; actual control requires current capability evidence. Reports expire after thirty minutes and become stale after a server restart. Supply the concrete `browser_id` when known, along with host/profile identity. Recheck the selected profile before authenticated operations. Website-specific blocks remain separate from a global browser capability.

Inspect the live account menu or a protected page/composer in that exact browser profile. An account label plus usable protected UI supports signed_in; an explicit login prompt or current unauthorised response supports signed_out/expired. A generic account icon, public page, cached markup, presence of cookies or eBay application API credentials does not prove buyer sign-in. Use unknown for timeouts, challenges, partial rendering or conflicting evidence. If the supported host exposes network response metadata, a current authenticated account response can support the check; keep cookies, session tokens, request headers and private payloads out of reports. Do not log the buyer out to test the guest case. Check guest state only in an already separate guest profile or a buyer-approved test account.

Settings uses the device's detected default browser. Read `device_browser` from `get_goodfinds_workspace`; an unavailable result stays unknown. Use the supported capability inventory for that selected browser and its connection flow. Offer another available route only as a user choice. Let the user sign in or resolve a challenge, then check again. Leave passwords, cookies and tokens in the browser.

The Settings **Check** action queues a durable job and asks the current buying agent to dispatch a native background subagent. Follow [connection checks](background-work.md#connection-checks) for dispatch, claims, leases, completion and unavailable-delegation recovery. Browser capability comes from the worker’s actual host tools for the selected route; there is no plugin-owned runtime or foreground fallback. Read progress with `get_goodfinds_connection_check` and stop queued/running work with `cancel_goodfinds_connection_check`.

## Listing contact and native offers

Before exposing or preparing seller contact, inspect the canonical saved listing in the selected browser profile. Use `report_goodfinds_listing_contact` with the current revision and access_context, exact listing_key/URL, marketplace, browser, host/profile, evidence, and separate message/offer availability. Available means the enabled interface is usable by this buyer, not merely that button text appears in HTML. Removed, reserved, sold, disabled, blocked or login-only controls do not establish usable contact. Report unknown when inspection is blocked; do not infer unavailable from a failed page load. Recheck reports after thirty minutes, a host restart, a profile change, or an observed restriction.

Report message_auth and offer_auth separately: required, not_required or unknown. Default to required; not_required needs evidence of a usable guest route without a later authentication requirement. A fresh signed-out observation can enable only an explicitly verified guest route; unknown/expired account state remains blocked. Facebook messaging and Craigslist CL Chat require an account regardless of a guest-route report. A guest composer does not prove guest access to native offers. Import updated listing availability evidence when the saved status disagrees with the page; a contact report does not itself change listing availability.

Use message: available only for an on-platform seller composer or chat. Call, email relay, seller website and callback forms are external contact; record external_contact and leave marketplace messaging unavailable when that is the only route. These listings expose Open listing without Negotiate. Existing conversation history remains readable. Some Auto Trader dealers offer chat; Craigslist supports opt-in CL Chat as well as email relay. Inspect the listing instead of assigning one contact mode to an entire marketplace.

Negotiation is supported when at least one verified offer or message route is usable. Prefer a native offer plus a brief personal message when both are available. Inspect and report offer_note separately: available only for a usable message/note field inside the native offer form. Prefer that field for the companion text; otherwise use a verified standalone seller composer. An offer note can supply the personal message even when general seller messaging is unavailable. Unknown note support needs inspection, not a guessed field or a claim that messaging is impossible. If only a native offer or only messaging is usable, expose that route; if neither is usable, hide Negotiate.

Show the buyer the exact amount and companion text together, using the same price and only their stated commitments. A saved matching draft may supply the wording; changed amounts or wording require renewed review. Avoid sending the same personal message twice when the offer form already includes it, unless the buyer chooses an additional follow-up. Inspect existing offer/message history before retrying. A native offer and its companion message have separate outcomes: confirmation of one never establishes the other was sent. If only one completes, retain its confirmation and retry only the unfinished part after inspection. Do not silently downgrade a requested native offer to messaging because its amount or quota is invalid.

Native Make offer and free-text messaging are different interfaces. eBay Best Offer depends on a listing's Make Offer control; Ask seller does not imply Best Offer. Vinted Ask seller and Make an offer are separate. Inspect the actual offer form without submitting; record offer_limits only from current form or applicable primary documentation: currency, minimum/maximum in minor units, increment and remaining offers, with null for unknown bounds/quota. An unknown limit is not zero and an absent quota is not unlimited. Preserve evidence distinguishing item price from delivery, buyer protection, bundles and regional rules. Do not hardcode an unverified Vinted 40% discount floor. A chat message cannot submit a native offer or establish that its limits were met; choosing a message-only seller conversation remains a distinct buyer choice. Where evidence establishes a 40% maximum discount, the corresponding floor is 60% of the applicable item price; the platform's displayed rounded amount takes precedence.

Goodfinds currently executes reviewed Facebook messages only. Other observed marketplace composers support reviewed copy/open and user-reported history. Native offers use a separate platform-form handoff; Goodfinds does not submit, automatically accept, pay, or mark these offers sent. Open and prepare only the buyer's chosen amount after refreshing eligibility and bounds, then stop for their review before any submission or commitment. eBay forms can request payment/postage details and autopay; a generic seller-message approval does not authorise that flow. A submitted native offer needs a future dedicated adapter and durable confirmation protocol before automated sending can be described as supported.

## Location

Location actions belong on the user's device. `open_goodfinds_location_chooser` returns a device-local five-minute page that can save location once. Open it only in a browser on the same user device as this local MCP server. Let the user click the button and answer location permission themselves. Opening the page does not grant browser automation permission.

Device coordinates are reverse-geocoded directly in that same browser before their result is saved. The free BigDataCloud client endpoint accepts fresh consented device coordinates, not stored coordinates or another provider's IP estimate. The separate IP action uses ipwho.is's approximate coordinates and existing locality fields; host web search or a cloud MCP call cannot identify the user's device location.

Show the returned area for confirmation. Keep source, acquisition time, country and accuracy/uncertainty. User changes to area or postal input need a new preview rather than reusing contradictory coordinates. An IP estimate and a nearby postcode do not establish a home address. ChatGPT can explain API results, but geocoding needs actual provider evidence.

Use the chosen country for postal labels and validation, preserving leading zeros. Locale is only an initial suggestion. Great Britain uses Postcodes.io; Northern Ireland commercial postcode lookup needs licensed data. Other country lookups depend on provider coverage. Manual area entry remains available. A manual area with unresolved coordinates must not produce invented journeys. Confirmed origin changes invalidate old journey evidence; rental target areas remain independent.

## Research and feedback

Persist `discovery` in drafts and searches: `scope` is exact, alternatives or help_choose, `reference_model` is optional except for exact, and `model_attribute` names its listing evidence field. WorkspaceStore sourced research, dates, queries, verified candidate capabilities, trade-offs and uncertainty. Only exact scope imposes the reference as a model constraint. Use `model` or the specified attribute in comparison cohorts so alternatives retain model-specific price evidence. Preserve must-haves in typed fields; research suggestions are not user preferences.

Read saved `config.feedback` before planning and collecting. `record_goodfinds_listing_feedback` keeps original wording and defaults to search scope. A reasonless dismissal affects that listing. Damage or a seller problem is not a model ban. For an explicit model rejection, pass `exclude_model: true`; the server derives a required `neq` rule only from the saved verified model. The panel labels this action **Exclude this model from this search**, separate from listing-only Disregard. Known aliases are excluded in eligibility, default listing views and model-specific queries; category discovery remains available. Old “Not interested in this model” feedback is upgraded when its saved model is verified, preserving event ID, wording, scope and Undo. Unidentified models stay listing-only and need identity clarification before a broader ban. An explicit capability need can become a rule; use `eq`, `gte` or `lte` for an explicit capability need. Numeric values must come from the user. Use required for must-haves and preferred for ranking. Scope category/global only with the buyer's choice.

Shortlist and more_like are learning signals, not proof the user wants every feature of the item. For more_like, research analogous options and explain their trade-offs; preserve existing hard requirements. When a reason leaves an important ambiguity, ask the one needed question before storing a broad rule. `undo_goodfinds_listing_feedback` restores the previous effective preference. To edit feedback, record a buyer-confirmed replacement and undo the superseded event using fresh revisions. Show learned preferences and their scope; suitable listings remain visible when bargain evidence is insufficient.

## Uncertainty and duplicate questions

Assign a unique `decision_id` to each generated question. The validator rejects repeated decision IDs; also compare question meanings with the brief and all existing questions because wording alone cannot detect semantic duplication. Preserve independent conditional details with separate IDs.

Use `allow_unsure: true` when a question reasonably needs help choosing. Native questions return `needs_guidance` and persist its ID in the draft's `uncertain_fields`, leaving its matching answer absent. Offer explained examples, research the remaining trade-off or propose an optional preference. Resume that field only after guidance; do not convert uncertainty into a guessed requirement or explicit no preference. Essential required uncertainty must be resolved before a final save. Keep the short setup budget and review step.
