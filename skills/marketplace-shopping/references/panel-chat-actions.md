# Panel and chat actions

The panel and agent share one backend. Persistent panel changes call the same MCP mutations available in chat; the local preview routes those tool calls to the same service. Use scoped entity revisions for persisted edits and the conversation's `version` for buying actions; follow [tool contracts](tool-contracts.md) for retries and conflicts. A successful mutation updates durable state for either interface; the panel refreshes it without a separate edit.

## Show the search at the right time

Keep one Goodfinds panel in the buying chat across searches and turns. Before the first display, inspect the chat's prior tool results and, when available, its open app tabs. Reuse an existing panel, including one opened during setup or by the buyer. A new search ID, edited brief, worker handoff or completed run does not need another panel. Run idempotency only reuses backend work: every `start_goodfinds_search` or `open_goodfinds_panel` call can request another host tab, even with the same request UUID.

For a direct buying request that still needs its first display, save the ready brief, confirm an executor is available, then call `start_goodfinds_search({request: {search_id, request_id, trigger: "manual"}})` once through the connected host. Claim or dispatch the returned run; the panel truthfully says waiting until execution begins. Show it before the cover follow-up, browsing or schedule setup. Its immediate category illustration updates when the product photo is saved.

After that display, save brief refinements and reuse the current run. When another run is needed, use `request_goodfinds_search_run` with the appropriate manual or scheduled trigger. After a failed or uncertain start, inspect `list_goodfinds_search_runs` before retrying through the non-displaying request tool with the same request UUID. Polling, cover updates, listing imports and final result delivery use non-displaying tools; the existing panel refreshes automatically. A later `open_goodfinds_panel` call is not a refresh or focus operation.

Orient a first-time buyer in one sentence: “Your search is in Goodfinds beside this chat; listings will appear there as I check them.” Say this only when the host has displayed the panel. Keep chat for meaningful findings, questions and interruptions. If the buyer closes the panel, keep working quietly until they ask to show it again. Missing tab inventory alone does not establish that a previously displayed panel needs reopening.

When browsing cannot launch, present the saved search in the existing panel, or use `open_goodfinds_panel({search_id})` for its first display, and explain the interruption in chat. Keep the run unqueued until an executor is available. Scheduled wake-ups and collection workers always use non-displaying tools. Reuse runs already queued by the panel. Multiple searches share the same panel.

If `start_goodfinds_search` is unavailable, queue through `request_goodfinds_search_run` and use `open_goodfinds_panel` only for the first display. A CLI/helper response cannot display a host panel. With no connected panel tool, keep saving and presenting results in chat and explain the display limitation briefly.

## Reuse and focus an existing panel

In Codex, Goodfinds is an MCP App tab, separate from marketplace tabs in the in-app browser. Use the host's current browser documentation. With `cua_repl`, list `cua.listTabs({browser: "mcpapps"})`, identify Goodfinds from the returned title/URL, and bind its observed ID with `cua.getTab(id, {browser: "mcpapps"})`. Inspect its DOM and use visible search/listing controls to present the requested item in that panel. If several Goodfinds tabs already exist, reuse one; leave the buyer's other tabs intact.

Binding a tab gives control but does not prove visible focus. Use an advertised host focus control when available, or select the existing tab through observed native app UI. The current MCP Apps browser API has no dedicated focus method and cannot create or navigate tabs. Use IDs with the provider that returned them; pass an app-tab ID to an ordinary browser opener only if the host explicitly supports it. If focus is unavailable, keep the result in the existing panel and explain where it is in chat; calling an opener again does not solve focus safely. Inline apps may be absent from the app-tab inventory; use the host's existing app expansion control when available.

For an explicit request to show saved results, reuse and focus first. If the buyer closed the panel and wants it back, call `open_goodfinds_panel({search_id, listing_key})` once with the known target fields. No new run is needed. The one-panel rule is an agent workflow; the plugin cannot enforce host tab uniqueness or confirm a display from a successful tool response alone.

`list_goodfinds_listings` filters before pagination. Seller filters use `minimum_listings`, `maximum_listings` and a `joined_by` year. Omit a limit for Any. Unknown/stale counts cannot establish a requested range; lower bounds establish only limits they prove. Disregarded items stay hidden unless `include_dismissed: true`. Price sorting groups currencies and rent periods rather than comparing unlike amounts. Use `get_goodfinds_listing` when an individual item's evidence is needed.

Tab changes, expanded sections, carousel position and unsaved form text are local presentation. An agent can read the corresponding information or save the same final change without operating those controls. Device location permission and external sign-in still use their supported host/browser flows. Saved video transport remains app-only to keep large encoded files out of model context; its agent equivalent returns the managed local file, which local hosts can preview. For hosts without file access, playback remains in the panel.
