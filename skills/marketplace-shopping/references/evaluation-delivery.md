# Evaluation and delivery

Use MCP imports for the shared workspace. For a standalone deterministic evaluation, export its current configuration from SQLite before supplying JSON to the bundled helper:

```sh
/absolute/plugin/root/server/goodfinds export --db /absolute/path/workspace.sqlite --output /absolute/path/exported-searches.json
/absolute/plugin/root/server/goodfinds evaluate --workspace /absolute/path/exported-searches.json --observations /absolute/path/observations.json --db /absolute/path/workspace.sqlite --report /absolute/path/report.html
```

The helper retains platform identities, original date evidence, sellers, descriptions, specifications, full prices, immutable observations, change events, failed checks, collection coverage, metric-specific eligibility and a durable alert outbox. The shared model accepts supplied observations from Facebook Marketplace, eBay, Vinted, Gumtree, Craigslist and UK Auto Trader; Facebook has the implemented browser workflow; eBay has a server Browse API adapter, while other sources expose navigation/import routes. Frequency summaries require repeated stable complete searches and original publication evidence. Observed active-period bounds and unfinished periods do not establish transaction times. Long age and isolated cheapness are context flags, not reasons to delete history. It prepares alerts; it does not deliver messages. Show each alert's listing link, price, specification and condition evidence, travel estimate, peer count, average asking price, and percentage below that average. Reference averages describe the observed sample, not all Marketplace inventory or completed sale prices.

Use the separate credibility result to hold an unusually low price combined with a recent seller account or an observed missing custom profile image for review. Keep those observations in history and explain the concrete signals; exclude them from automatic deal alerts. An older account with many visibly reported friends is supporting credibility evidence; show the age and count behind that conclusion. Hidden counts stay unknown. Supporting evidence does not clear conflicting item details or an existing price-and-seller review flag. A review flag is not a finding of fraud, and supporting profile evidence does not verify a seller or listing. The arithmetic average remains the deal rule; median and sample standard deviation are diagnostics for this additional check.

Confirm the alert repeat preference during setup. The default prepares one alert on first qualification and another only when the qualifying price falls below the lowest price previously queued for that search and rule set. Use `--help` for delivery acknowledgements and status. Acknowledge alerts only after successfully presenting them through the chosen notification channel. Pending alerts remain available when delivery fails. Browser interruptions or missing comparisons are run status, not deal alerts.

## Scheduling and verification

Monitoring is part of setup and search completion, including partial searches. Read get_goodfinds_search_context: it returns absolute storage paths and each search's monitoring preference, observed host receipt, status and next_action.

### Search hours and timing

Quiet hours default to **22:00–08:00 in the device's local time zone**. Scheduled searches skip that window; an explicit manual search can run then without changing monitoring. Settings → Search hours lets the buyer change the window, time zone or turn quiet hours off. Save the complete `quiet_hours: {enabled, start, end, timezone}` through `save_goodfinds_settings`. Use a valid IANA zone such as `Europe/London`, so clock changes follow local time. Start and end must differ. Do not ask the buyer to confirm these defaults during normal setup.

`set_goodfinds_monitoring` accepts `interval_minutes` (15–1440, hourly by default), or `timing: {mode: "daily", times: ["08:15", "18:30"]}` for up to 12 unique local daily times. A specific-time request should use `timing`, not an invented recurrence rule. An explicit request for overnight checks on one search sets `allow_quiet_hours: true`; otherwise keep the existing choice or the false default. Explain any returned `plan.excluded_times`. If all daily times are excluded, keep that choice visible and pause the linked automation rather than silently allowing overnight searches. For daily timing, the receipt's daily cadence summary is `interval_minutes: 1440`; the compiled plan defines the actual times.

Individual `monitoring.plan` describes that search's timing. Configure the host with the **shared `get_goodfinds_dispatcher_context` plan**, following [shared scheduling](scheduled-dispatch.md). Its recurrence is the union of eligible members' wake-up times; each search retains its cadence. Regular daytime intervals restart at the end of quiet hours; nonexistent local clock-change times are skipped and repeated local times start at most once. An unusual interval may still need the server guard. Quiet-hour and timing changes apply to execution immediately and may require updating the shared recurrence. Preserve observed host pauses; do not create extra automations to toggle quiet hours.

An explicit recurring instruction or established recurring preference authorizes monitoring in its original buying chat. Save preference `recurring` and the requested timing; an explicit one-off instruction is `once`. If undecided, show useful initial results and ask one concise **Search once** / **Keep watching hourly** choice, allowing custom timing. Saved criteria, enabled evaluation and an hourly default alone do not authorize monitoring. A development or review request cannot activate a buyer's search.

For authorized setup, validate the selected browser route through the initial manual search, then complete shared host registration. A status read checks already-linked automation metadata without creating or resuming schedules. For unlinked legacy automations, verify storage paths, search IDs and the original buying chat before adoption. Ambiguous matches stay unverified. Use the host's supported scheduling tools and record actual evidence; Goodfinds has no internal clock or notification transport.

Show **Monitoring active** only after the actual shared automation, recurrence, time zone and original chat are verified. **Quiet hours** means a verified schedule is resting; **Schedule update needed** means the host recurrence differs from the saved plan. Local execution requires the device awake and the host app running. A registered schedule does not prove a successful unattended run: keep the first run pending until actual search completion. Goodfinds records successful execution separately for each search; a shared host wake-up cannot establish that every member ran. Notify substantive new or changed findings, failures and needed buyer choices; routine empty batches and unchanged results remain quiet. Seller sends and purchases still need their existing review.

Pause, resume, remove and timing changes use the same shared registration workflow. Stopping one member preserves eligible peers. Only pause the host when no members have permitted times, or when the buyer explicitly pauses the entire group. Removing a search retains its listing and run history. Report concrete interruptions and retain verified receipts for retry.

Run the synthetic demonstration independently with `/absolute/plugin/root/server/goodfinds demo --output /absolute/path/demo-output`. Synthetic prices, sellers, locations, schedules and alerts must be labelled as examples.
