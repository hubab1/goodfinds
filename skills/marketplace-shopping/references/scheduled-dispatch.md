# Shared scheduling

## Register or reconcile

1. Read the current search context and its absolute storage paths. Preserve one-off, undecided, disabled and fulfilled choices. Recurring monitoring must already be authorized in the original buying chat. Use `get_goodfinds_dispatcher_context` with that `thread_id` and explicit proposed `search_ids`, or an existing `dispatcher_id`. Inspect existing dispatcher members and legacy receipts before any host change. Keep the original host and host notification policy. Do not move monitoring into a development chat.
2. Join an existing compatible dispatcher in the same chat, host and notification policy. Include its continuing recurring members in the proposed context call; keep disabled recurring members so they can resume later. Remove members changed to one-off after preserving peers. Use the returned `plan.rrule`, `plan.timezone` and `plan.interval_minutes`, rather than a member's individual recurrence. The plan covers eligible wake-ups, not every search at every wake-up. If `supported` is false, group searches with representable timing plans separately; do not invent a frequent polling rule or silently change their requested cadence. A plan with no permitted times pauses the host.
3. Reuse the registered automation ID. For legacy migration, prefer an existing automation matching the proposed union, then pause and verify each redundant legacy automation through the host. Record those observed pauses with `report_goodfinds_host_schedule` and fresh per-search revisions before clearing their legacy bindings. Do not register a shared group while a redundant legacy automation can still execute. If a pause or host update fails, keep the existing receipts and report the concrete blocker.
4. Use the host scheduler to create/update the shared automation in its original buying chat. In Codex use `automation_update` with kind `heartbeat`; preserve the target chat and all unrelated fields on updates. A standalone task needs the buyer's request. Save a cohesive prompt containing the dispatcher UUID, original thread UUID and absolute workspace paths, directing the wake-up to the latest installed marketplace-shopping skill and the batch steps below. Search IDs and criteria come from the database at execution time; never freeze them into the prompt. Keep notification preferences in host settings. Preserve observed external pauses unless resuming is authorized.
5. Verify the actual automation ID, target chat, status, recurrence and supported time zone from the host result and saved metadata. Read a fresh dispatcher context, then call `report_goodfinds_dispatcher_schedule` with the current settings `expected_entity_revision`, `report.plan_revision: plan.revision`, dispatcher identity, complete member IDs and verified `schedule`. The schedule contains the real automation/thread IDs, status, interval summary, actual rule, zone and evidence. Use host-observed next/last wake-up times only, otherwise null. Shared wake-up timestamps are not individual successful search timestamps. A blocked report records an interruption without replacing a verified receipt.
6. On a single member's pause, disable, fulfilment or removal, recompute the union for remaining members. Keep their monitoring choices and workers. An unchanged union needs no host recurrence edit; verify and refresh the shared receipt. A narrower union updates the same automation; no eligible members pauses it. Resume only with authorization and reuse the same binding. External group pauses apply to all members and cannot be undone by a status read. Do not report completion until host state is verified or a concrete blocker is visible.

## Execute a shared wake-up

Call `request_goodfinds_scheduled_batch` **first**, with the saved `dispatcher_id`, original `thread_id` and a fresh UUID `request_id` retained for retries of this wake-up. The server checks observed shared host state, individual eligibility, cadence, quiet hours and prior starts, then atomically reserves due runs. No catch-up runs are created. An empty batch returns quietly without listing context, browsing or a new worker. A timing mismatch requires registration reconciliation; a paused or unverified host requires reporting that state, not automatic resumption.

Reread each returned run before spawning: a replayed wake-up receipt contains its original result, so versions and ownership may have advanced. For returned runs with a live worker, reuse it; never spawn a competing agent. Returned unclaimed runs are already requested: do not call `request_goodfinds_search_run` again. Read each current scoped context and dispatch through [background work](background-work.md), preserving model routing, saved browser route, query coverage and per-run claims. Limit collection to the host's available worker capacity. Separate tabs may run concurrently only when the browser tool supports independent tab control. A shared foreground browser requires one collection worker to process the reserved runs sequentially, claiming and completing each independently; never let concurrent workers navigate the same foreground tab.

A sequential batch worker refreshes every waiting unclaimed run at least once a minute with `update_goodfinds_search_run`, its current `expected_version`, unchanged phase `requested` and truthful `next_step`. Claimed runs use their normal lease renewal. Reread versions and worker ownership before claiming; if a peer claimed a waiting run, leave it to that worker. Pending reservations expire after five minutes when not refreshed. If capacity or delegation is unavailable, mark those runs blocked with the actual reason; their next due check can resume saved coverage. Never claim execution simply to keep a queue alive.

If a returned live worker already controls the shared foreground browser, send new unclaimed run IDs to that same worker through the native follow-up channel for sequential processing. Do not launch another browser controller while it is active. Each run keeps its own worker UUID and lease even when one native agent executes several runs.

The buying chat returns after background dispatch. The worker uses current briefs, broad and exact discovery, incremental evidence imports and per-search terminal outcomes. A failure in one member does not cancel other eligible runs. During browser work, leases, updates and imports still recheck quiet hours, enabled/fulfilled status and the shared pause. Close owned temporary tabs on completion or interruption. Save actual success per search; the server updates its successful scheduled-run timestamp only after a completed scheduled run. Prepare useful next buying actions, while seller sends and purchases retain their existing review.

If the exposed tool list predates shared dispatch, use the latest installed [packaged protocol helper](connection-diagnostics.md#connection-diagnostics-and-fallback). Do not replace the batch with one host automation per search.
