# Shared scheduling

## Compatibility after an upgrade

Read `get_goodfinds_runtime_context` for the installed contract and saved binding compatibility. Missing version evidence is `unknown`; a different contract is `stale`. Verify the saved host prompt resolves the current installed `marketplace-shopping` skill before reporting `schedule.workflow_version` from that contract and `schedule.skill_name: "marketplace-shopping"`. These fields record the caller's verification, not server inspection of the host prompt. Perform any authorized update in the original buying chat while retaining observed pauses, cadence, notification choices and thread identity. A diagnostic read or development request never activates monitoring.

## Register or reconcile

1. Read the current search context and its absolute storage paths. Preserve one-off, undecided, disabled and fulfilled choices. Recurring monitoring must already be authorized in the original buying chat. Use `get_goodfinds_dispatcher_context` with that `thread_id` and explicit proposed `search_ids`, or an existing `dispatcher_id`. Inspect existing dispatcher members and verified receipts before any host change. Keep the original host and host notification policy. A development request does not authorize moving monitoring. An explicit buyer Start checks, Resume checks or Restore schedule request can use the recovery steps below if its original chat is unavailable.
2. Join an existing compatible dispatcher in the same chat, host and notification policy. Include its continuing recurring members in the proposed context call; keep disabled recurring members so they can resume later. Remove members changed to one-off after preserving peers. Use the returned `plan.rrule`, `plan.timezone` and `plan.interval_minutes`, rather than a member's individual recurrence. The plan covers eligible wake-ups, not every search at every wake-up. If `supported` is false, group searches with representable timing plans separately; do not invent a frequent polling rule or silently change their requested cadence. A plan with no permitted times pauses the host.
3. Reuse the registered automation ID. If a pause or host update fails, keep the verified receipt and report the concrete blocker.
4. Use the host scheduler to create/update the shared automation in its original buying chat. In Codex use `automation_update` with kind `heartbeat`; preserve the target chat and all unrelated fields on updates. A standalone task needs the buyer's request. Save a cohesive prompt containing the dispatcher UUID, original thread UUID and absolute workspace paths, directing the wake-up to the latest installed marketplace-shopping skill and the batch steps below. Search IDs and criteria come from the database at execution time; never freeze them into the prompt. Keep notification preferences in host settings. Preserve observed external pauses unless resuming is authorized.
5. Verify the actual automation ID, target chat, status, recurrence and supported time zone from the host result and saved metadata. Read a fresh dispatcher context, then call `report_goodfinds_dispatcher_schedule` with the current settings `expected_entity_revision`, `report.plan_revision: plan.revision`, dispatcher identity, complete member IDs and verified `schedule`. The schedule contains the real automation/thread IDs, status, interval summary, actual rule, zone and evidence. Use host-observed next/last wake-up times only, otherwise null. Shared wake-up timestamps are not individual successful search timestamps. A blocked report records an interruption without replacing a verified receipt.
6. On a single member's pause, disable, fulfilment or removal, recompute the union for remaining members. Keep their monitoring choices and workers. An unchanged union needs no host recurrence edit; verify and refresh the shared receipt. A narrower union updates the same automation; no eligible members pauses it. Resume only with authorization and reuse the same binding. External group pauses apply to all members and cannot be undone by a status read. Do not report completion until host state is verified or a concrete blocker is visible.

## Recover a removed schedule

Start checks, Resume checks and Restore schedule are explicit authorization to activate the named search, enable it if needed, and preserve its saved cadence and quiet hours. Check status is read-only authorization. Keep a working original chat and reuse an existing schedule whenever possible.

If the original buying chat is unavailable, recover into the current buying chat only after the old automation is freshly verified **removed**. A paused or unavailable schedule remains bound to its original chat; resolve that status before creating a replacement. The panel's explicit start/resume request authorizes this fallback without another conversational confirmation. Tell the buyer that future updates will arrive here.

1. Read the search context to identify its previous dispatcher, host and notification policy. Save preference recurring and enabled true only for the requested search. Preserve every peer's preference, timing and enabled flag.
2. Read `get_goodfinds_dispatcher_context` with the current `thread_id`, the requested `search_ids` and `recover_removed_search_ids` containing only the explicitly requested IDs. The server checks fresh host removal evidence. Join a compatible dispatcher here, including its continuing members in `search_ids`; keep recovery IDs restricted to the searches being moved.
3. Create or update the target heartbeat with the returned plan through the host scheduling tool. Preserve the source host and notification policy. Use a new dispatcher UUID for a new group; an existing compatible target group keeps its UUID and automation ID.
4. Verify the target automation, then reread context and report its current plan revision through `report_goodfinds_dispatcher_schedule`, including the same `recover_removed_search_ids`. This atomically moves those memberships while retaining the old group's other members and all per-search execution history. A blocked report leaves membership unchanged.
5. Show active only after host verification. If registration succeeds but saving its receipt fails, retain the returned automation ID for retry and reconcile that same automation; avoid creating another replacement.

## Execute a shared wake-up

Call `request_goodfinds_scheduled_batch` **first**, with the saved `dispatcher_id`, original `thread_id` and a fresh UUID `request_id` retained for retries of this wake-up. The server checks observed shared host state, individual eligibility, cadence, quiet hours and prior starts, then atomically reserves due runs. No catch-up runs are created. An empty batch returns quietly without listing context, browsing or a new worker. A timing mismatch requires registration reconciliation; a paused or unverified host requires reporting that state, not automatic resumption.

Reread each returned run before spawning: a replayed wake-up receipt contains its original result, so versions and ownership may have advanced. Reuse a live worker for that run. Returned unclaimed runs are already requested: do not call `request_goodfinds_search_run` again. Read each current scoped context and dispatch independent searches in parallel through [background work](background-work.md), within host capacity. Preserve model routing, the saved browser route, query coverage and each run's claim. Each worker must acquire its own successful claim before browser work and close only its own tabs on completion.

When host capacity leaves a reserved run waiting, refresh its current version and ownership before dispatch. Refresh waiting unclaimed reservations at least once a minute with `update_goodfinds_search_run`, their current `expected_version`, unchanged phase `requested` and a truthful `next_step`. Reservations expire after five minutes without progress; claimed runs use their normal lease renewal. If a peer claimed a waiting run, leave it to that worker. If capacity or delegation is unavailable, mark affected unclaimed runs blocked with the actual reason; their next due check can resume saved coverage. Claim only when execution can begin.

Follow the completion-continuation rules in background work; dispatch alone is not completion. The worker uses current briefs, broad and exact discovery, incremental evidence imports and per-search terminal outcomes. A failure in one member does not cancel other eligible runs. During browser work, leases, updates and imports still recheck quiet hours, enabled/fulfilled status and the shared pause. Close owned temporary tabs on completion or interruption. Save actual success per search; the server updates its successful scheduled-run timestamp only after a completed scheduled run. Prepare useful next buying actions, while seller sends and purchases retain their existing review.
