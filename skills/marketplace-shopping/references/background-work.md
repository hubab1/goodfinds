# Background work

## Independent searches and ownership

Independent saved searches may execute in parallel across chats and scheduled wakes, within the host's available worker and browser capacity. Each search keeps its own run, worker UUID, lease and owned tabs. Reuse the active run and its live worker for the same saved search. A successful claim must return your `worker.id` and a discovering/verifying phase before browser work or evidence imports. A requested run without a worker is awaiting a claim. Renew only your acquired lease and use the latest returned version. If a browser action requires shared foreground control, coordinate that action with the other worker; this does not impose a workspace-wide search limit.

## Dispatch from the buying chat

Use `get_goodfinds_runtime_context` when checking host support or recovering after an upgrade. Report actual capability observations through `report_goodfinds_host_capabilities` in the same access context with the current evidence revision. A listed tool is `advertised`; a successful observed action is `observed`; an established missing route is `unavailable`; leave unverified support `unknown`. Reports expire after 30 minutes and do not establish marketplace sign-in or seller permission. Capability observations from another connection cannot establish this worker's access.

For a direct human request on one marketplace, the buying chat may execute the claimed run itself when its selected browser is available. Authorized scheduled collection can also use the owning-chat recovery below when browser access is scoped to that chat. Follow the same request, claim, lease, cancellation, coverage and completion rules, using the actual runtime agent identity. Connection checks and an explicit background-only request keep their delegated path.

1. For a shared scheduled wake-up, follow [shared batch execution](scheduled-dispatch.md#execute-a-shared-wake-up): call `request_goodfinds_scheduled_batch` first and use its reserved runs. Do not request those runs again. For a permitted wake-up or human request, read the latest installed skill and `get_goodfinds_search_context` for that scope. Reconcile the linked schedule during permitted scheduled work. A one-off request may check a paused search without changing monitoring.
2. For a human request, queue and display the search through [panel handoff](panel-chat-actions.md#show-the-search-at-the-right-time). Reuse supplied runs already queued by the panel. The request UUID belongs inside `request`. If the server returns a disallowed `scheduled_check`, return quietly. If its phase is active and `worker` is present, reuse that worker: report saved activity only when useful and return. A new click or scheduled wake-up must not reset progress or launch an overlapping search.
3. Use the host's native subagent tool (`collaboration.spawn_agent`, or the host's equivalent), one collection worker per independent saved search, allowing parallel dispatch within host capacity. Apply the launch settings from `workflow.actions[].execution` and the generated [worker model routing](state-model.md#worker-model-routing). Pass the model, reasoning effort and context-fork choice as native launch arguments, rather than asking an already-running worker to switch itself. Supply the search/run IDs, a fresh UUID `worker_id`, absolute shared storage paths, installed skill path, saved browser route, current brief/query plan and any explicit buyer constraints. Preserve the buying chat's permissions. The worker verifies its own browser availability; parent access and another worker's limitation do not establish its access. Preserve the saved route; changing it requires the buyer's choice. The worker creates and closes only its own tabs.
4. Give a short progress acknowledgement after dispatch and ensure the original buying chat will consume completion, deliver results and finish pending monitoring setup. End the turn early only when a supported host continuation actually resumes this chat after child completion. A child result notification alone may not start a new buying-chat turn. Without that continuation, keep this turn active with the native agent wait tool, respond to new buyer input, and consume the worker's result when it arrives. Leave browsing and gallery review to the child. If native delegation is missing or launch fails, mark the unclaimed run blocked with the actual interruption and next step. An acknowledgement or saved request alone is not a finished search.

The child prompt must tell it to resolve any pending [search cover](search-covers.md) as its first bounded media task, follow the worker steps below and [search workflow](search-workflow.md), use the latest saved brief rather than stale chat criteria, preserve photo/video capture, and report terminal status even when interrupted. Pass current cover metadata and whether a follow-up is pending. Include the exact navigation reference path: `references/marketplace-navigation.md` for eBay, Gumtree, Facebook or AutoTrader; `references/vinted-clothing.md` for Vinted clothing. Load that guide before the first marketplace tab, observations before importing, and state-model only for a returned guard. Read each file separately or request bounded sections; concatenated references and full run receipts can truncate the instructions in the middle. One fresh scoped context read is enough before claiming; returned resources carry subsequent versions. It must not dispatch further search agents. Collection workers save explicit evidence and return ambiguities or conflicts to the buying chat for judgment. Setup choices, final comparisons, schedule creation/changes and outgoing seller-message review/sends belong to the original buying chat.

Search dispatch uses `browser_collection`: pass `fork_turns: "none"` and omit model/reasoning overrides, inheriting the buying chat's selected settings. If mounted workflow metadata still recommends a different search profile, obtain the current run workflow from the installed helper before dispatching. Connection/contact/reply checks keep their separate collection profile.

## Recover interrupted searches

Separate a run's outcome from monitoring. A failed or expired worker leaves the buyer's enabled flag, recurring preference and host schedule intact. Each new permitted scheduled occurrence creates a fresh run and query plan; older partial or blocked attempts remain history. Reuse live workers and preserve coverage when recovering the same occurrence. Media-repair and journey queues persist independently, so an outstanding repair cannot make later checks reuse stale discovery. An explicit pause, cancellation or fulfilled goal remains authoritative.

Read `get_goodfinds_search_recovery` with the exact `run_id`. It returns the current brief and revision, owner/lease, workflow blockers, unfinished queries and pending verification references. Read all applicable feedback pages before resuming. Use `expected_version` and `expected_context_revision` from the first page with every nonzero offset; a conflict restarts paging. `include_brief: false` explicitly omits the brief and shared settings on subsequent pages. Verify browser access through the selected route in this connection. Preserve completed and skipped queries and already verified references. Use the separate media-repair and journey queues for missing supporting evidence. These projections grant no claim or seller-send permission; commands recheck eligibility.

After reconnecting or missing a child notification, read `list_goodfinds_coordination_events`. Reopen each referenced run through recovery and each alert through the pending-alert tool, then retain the returned cursor after processing the page. An event describes a committed change; the resource may since have changed. On `cursor_gap`, discard the cursor, reconcile current runs and pending alerts, and restart the feed. Duplicate consumption is possible. Never replay a seller send from a completion event. Lease expiry can appear in read-only recovery before the next mutation records its interruption event.

During a live search, recover a transient timeout or disconnected tab once: reread the current run and brief, confirm ownership and eligibility, then retry the failed read-only step with the same worker. After lease expiry, the original buying chat may replace that worker once for the interrupted attempt, retaining the trigger and preflighting scheduled eligibility. Repeated failure saves the concrete blocker and returns; the next scheduled check may try again. Preserve successful queries, imports and media. Stable import request IDs prevent duplicate writes. Seller sends use their separate reconciliation workflow.

For an expired scheduled worker within the same occurrence, stop the old child and call `request_goodfinds_search_run` with `request.request_id` equal to the original run ID, `resume: true` and `trigger: scheduled`. The server preserves its original scheduled time, query coverage and observations while clearing the expired owner. Claim that returned requested run with a fresh worker UUID and the replacement's actual agent identity. Current pause, quiet-hour, brief and live-owner guards still apply. An earlier occurrence cannot be revived this way; let the next due batch start fresh discovery. Do not change the trigger to manual or invent a new run to bypass those guards.

When the buyer opens Goodfinds or asks for progress, inspect interrupted runs alongside monitoring. For an already-authorized recurring search in its original buying chat, preflight scheduled eligibility and dispatch a due recovery automatically. A not-yet-due check waits for the existing schedule. Repair a removed or changed schedule only within the buyer's existing monitoring authorization, and preserve observed pauses. A saved one-off search needs a new search request after its bounded live recovery is exhausted.

## Browser available only in the buying chat

A child's missing selected browser establishes that connection's limitation. Verify the same route in the original buying chat. An available browser there can execute human-requested searches and already-authorized scheduled collection with hidden owned tabs; keep explicit background-only requests and connection-check jobs on their delegated path. Preserve the selected browser and account. Explain the executor change once; a status read alone does not authorize collection.

Choose the executor before claiming. Reuse a current observed child-route limitation instead of launching another child solely to repeat it. For an unclaimed run reserved by `request_goodfinds_scheduled_batch`, reread and claim that exact requested run directly in the original buying chat with a fresh worker UUID and the actual runtime agent identity. Keep its scheduled trigger and all quiet-hour, pause and cadence guards; do not request the reservation again. A child preflighting an unavailable route returns the limitation before claiming so this handoff remains possible. If neither connection can browse, record the concrete blocker.

For an interrupted human-requested run, confirm no live owner, resume through `request_goodfinds_search_run`, and claim the returned run. Preserve that run's coverage and observations. A conflicting live owner prevents takeover. Follow every lease, cancellation, import and completion guard below; leave unknown execution settings absent. Keep each run's ownership and tabs separate, and report owning-chat execution separately from background success.

## Execute in the search worker

1. Read the scoped context for initial setup, or `get_goodfinds_search_recovery` for a supplied run after interruption. Preflight the selected browser in this connection; an unavailable child returns that limitation before claiming so the buying chat can select an executor. Then call `claim_goodfinds_search_run` with `request: {run_id, expected_version, worker_id, agent_id, parent_thread_id?, execution?}`. Use your actual native agent ID or canonical task name from the runtime. Report actual host-provided model/effort through `execution` as described in [worker model routing](state-model.md#worker-model-routing); leave unknown settings absent. Never invent an agent identity. The UUID distinguishes attempts; retain it throughout the run. On an ownership conflict, reread and stop if another live worker owns the run.
2. Renew with `renew_goodfinds_search_lease`: `request: {run_id, worker_id}` at least once a minute, before lengthy work, and after a slow tool returns. Claims last five minutes. Progress updates and run imports also renew the lease. Every progress update includes `worker_id` and the latest `expected_version`; every run import includes `run_id` and `worker_id`. Use the returned run and version after imports, heartbeats and progress writes. Reread only when the response omits the current run or reports a conflict.
3. Before every browser step and write, verify that the run remains active, your worker ID matches and the buying brief is unchanged. Scheduled heartbeats, updates and imports enforce current quiet hours and enabled/fulfilled state. A disallowed `scheduled_check`, deferred phase, cancellation, expired lease or changed brief stops this attempt. Preserve results and close your own temporary tabs. A stopped agent cannot revive its lease or write late run imports; resume through a new dispatch at a permitted time. Do not announce routine quiet-hour skips.

   Use the compact `renew_goodfinds_search_lease` result when a browser batch needs a fresh ownership/eligibility check. It applies the server guards and returns the current run. Reuse a just-returned claim/progress/import result; a full search-context read is needed for initial setup, a changed brief or conflict recovery, not to rediscover the same phase and worker before every click.

4. Resolve a pending [search cover](search-covers.md) before marketplace discovery and gallery review. Reuse a saved photo or choose a suitable accepted-model/family photo, cache and attach it; keep this to one bounded attempt and maintain the lease. Then verify that your native browser tools can control the saved route before discovery. If unavailable, record blocked status with the actual route limitation and return it to the buying chat for the recovery branch above; leave other browsers untouched. An available Chrome bridge still requires observing the selected account's access and sign-in. All marketplace searches, including eBay, use that browser route. Then perform [broad discovery and shortlist verification](search-workflow.md), preserving platform permissions. Save useful observations incrementally, recover available photos/videos and review the required shortlist evidence. A heartbeat records activity, not query coverage or successful verification.
5. Save completed, partial or blocked status with evidence and a next step. Read prepared buying actions and return a concise result to the parent through the native agent completion channel. Notify only meaningful findings, failures or required buyer choices; routine activity belongs on the search row. For a scheduled run, record successful execution only after the actual search succeeds, preserving the linked schedule. Never mark execution successful at dispatch.

If the chat's exposed tool list predates these worker tools, use the latest installed [packaged protocol helper](connection-diagnostics.md#connection-diagnostics-and-fallback). Independent search-run calls can use `call TOOL --input FILE`; only context-bound access reports, connection checks and seller actions need one persistent helper client. Close helper processes you created when their work ends. Do not rebuild an MCP client or change the buyer's browser to work around stale tools.

## Connection checks

1. Read `get_goodfinds_connection_check` for the requested `run_id`. For a direct buyer request, first queue the selected marketplaces using `start_goodfinds_connection_check` with the current settings revision and a fresh request UUID. Settings **Check** already queues the job and sends its ID to the buying chat. Reuse a running worker; return saved terminal progress without spawning. A queued job means no worker has claimed it yet.
2. The parent dispatches one native background subagent using the returned `execution.spawn` settings. Pass the exact run ID, current access context, targets, shared workspace paths, installed skill and supported browser tools. Return after dispatch; leave browsing and polling to the child. If delegation is missing or launch fails, reread the check and use `interrupt_goodfinds_connection_check` on an unclaimed queued job with its current `expected_version`, `status: unavailable` and the actual reason. Keep the main chat available; there is no foreground browser fallback, separate CLI/app-server launch or user-owned chat creation.
3. The child reads the exact check through the same connected MCP tool session. Confirm its `context_id` matches the current workspace `access_context`; a different helper/host connection cannot reuse that observation context. Claim with `claim_goodfinds_connection_check`, passing the current version, a fresh UUID `worker_id`, actual native `agent_id`, `parent_thread_id` when supplied by the host and known actual `execution` settings. The claim is required before browser work. A competing claim means reread and stop. Identities and settings are caller-reported audit information, not host attestation.
4. Renew using `renew_goodfinds_connection_check` at least once a minute and before/after slow browser steps. The lease lasts two minutes; each claimed check has a five-minute maximum. Before each browser step, verify that the check is still running, the worker matches and the selected route is unchanged. Stop on cancellation, expiry or a changed route; close only the tabs you created.
5. Use the child's actual browser capability inventory to control only the selected routes. When a device browser ID is unknown, establish the selected device default from observed host evidence; leave it unchecked if that identity cannot be established. Inspect only new tabs at each target’s returned regional `url`. A null URL means the country has no supported route; omit that target instead of substituting a UK or US site. Record actual host/browser/profile identity and visible sign-in evidence; public browsing or a sign-in button alone does not prove signed-in access. Browser access and marketplace sign-in are separate observations. Leave passwords, cookies, tokens and account details in the browser. A check observes access only; sign-in, permission changes, challenges, listings and seller contact use their separate authorized workflows.
6. Reread/renew, then save paired observations using `complete_goodfinds_connection_check` with the owning `worker_id` and latest version. Omit unsupported targets; they remain unknown without refreshed evidence. If none can be checked, or execution fails, use `interrupt_goodfinds_connection_check` with that worker and the actual limitation. These check tools enforce ownership and cancellation; standalone browser/session report tools are not a substitute for completing a claimed check. Return a concise native completion result. Queued jobs expire after two minutes; late results cannot revive cancelled or expired work.

## Other actions

Delegate lengthy read-only work using [worker model routing](state-model.md#worker-model-routing): contact/reply checks use collection, while listing evidence and media recovery use browser_collection and inherit the buying chat's model. Pass existing action IDs and versions, preserve claim/cancellation checks, save the actual observations, then return a short result. Seller action claims also accept optional `execution` for known actual host settings. Keep scheduler changes, judgment and outgoing messages in the original buying chat with its model and reasoning and the existing exact reviewed draft/send permit. A request for background work does not authorize additional seller contact.
