# Broad discovery and shortlist verification

The steps below run in the current claimed executor. A direct single-platform search can execute in the buying chat's selected browser; use [background work](background-work.md) for delegation, scheduled work or ownership recovery. Queue and display a human-requested search through [panel handoff](panel-chat-actions.md#show-the-search-at-the-right-time), then claim its returned run as in step 1. Reuse a supplied run or active worker; do not create overlapping work.

For Vinted clothing, follow [department, category, native filters and recovery](vinted-clothing.md). Prefer usable native filters. If a filter stays empty or changes leave stale cards, use that guide's bounded recovery and broader discovery fallback before ending the run. Preserve the buying requirements through listing evidence and record the actual search scope; fallback results do not establish successful native filtering.

For eBay, Gumtree, Facebook Marketplace and AutoTrader, read the current platform's section of [marketplace navigation](marketplace-navigation.md), including its shared browser recovery and media checks.

Use the saved search’s `market` and returned `marketplace_routes[search_id]` to choose regional sites. Verify the actual collection location or delivery destination on each site, since browser sessions can retain an older region. Keep unavailable regional routes explicit in coverage.

Keep setup proportional to the search. Reuse a matching ready brief, saved cover and browser choice; do not resave unchanged criteria. Load observation details when preparing an import, seller-conversation guidance when preparing the next buying action, and recovery/state references only for the relevant branch. Inspect an unfamiliar tool's current schema once, retain it locally and print only the fields needed for the current action. Do not reread large schemas or every workflow reference before browsing.

Use returned run versions and listing keys throughout the run. Imports and progress writes renew the lease; make a separate renewal only when due or before lengthy work. Combine independent reads and media caching where supported, and keep dependent writes sequential. Fresh detail observations can import their newly cached photos, capture status and review together; a separate media attachment is for media-only repair, not a prerequisite to every verification import. Copy the returned listing_key instead of reconstructing its namespace.

In a persistent JavaScript runtime, keep changing run/worker state in one object and update its properties after each response. A helper must read that object's latest run version when constructing the next request; avoid closures over top-level variables redeclared in later cells. The protocol helper returns an MCP envelope: unwrap `structuredContent` (or its text JSON fallback), then read `search_run`, not `run`, from request/claim/progress results. Save complete local receipts, but print only the current phase/version, relevant result or error.

When the host supports tool orchestration, retain returned native results directly in its state or local files. Do not hand-transcribe a full run document from printed output just to update its version and a query. Keep only the required request fields and derive them from the latest returned resource.

Construct fresh observations from the currently rendered cards and details. Saved records may supply matching identities or cached media, but never copy saved prices, condition or availability into a fresh observation without confirming each value on the current page. Collect current card IDs dynamically; earlier candidates are leads to recheck, not today's result set.

For a request to find one item, read the visible result cards broadly and save an initial shortlist of at most two promising candidates. Preserve the actual result count in coverage. Add another candidate if those fail verification; wider comparisons and audits retain their requested scope. Every saved candidate still needs its required media capture.

Match verification depth to the buying request. For a request to find one item, inspect the strongest current candidate first and finish once a clear match has its required facts and entire gallery verified, query coverage is accounted for, and required media saving is complete. Inspect more candidates when the first is unsuitable or uncertain, the buyer requests a comparison or several options, or a material tradeoff needs evidence. A request for one hoodie is not an exhaustive audit of every candidate. Keep other discovery records provisional; completed query coverage does not claim their detail verification. Preserve full gallery capture for saved listings and repair ready missing media, but do not repeat completed media work or deeply verify every discovery card by default.

Once the requested number of verified matches is found, remaining optional alias or sibling-category queries can be skipped with that reason. Still cover every explicitly requested marketplace, garment type or comparison, and retain the required successful broad category query. Before completing the run, read the recommended listing's assessment and ensure every hard field has source evidence, including item type, department, brand, size and pattern for clothing. Correct missing evidence in the current owned run before completion; a matching attribute value alone may still be unsupported.

When an exact query and a broad query already cover the same category/filter scope, skip redundant generated aliases with that scope as the reason, even when no suitable candidate is found. Zero qualifying listings alone is not a coverage gap. Add a query only for a concrete missing model, category or observed search mismatch; do not restart discovery after detail review just to execute every generated wording. Report the sampled coverage and unresolved constraints without claiming market-wide absence.

After each query, filter or location change, verify both the visible controls and the rendered results. A changed URL or search field alone does not establish refreshed results. Compare result headings/counts and leading listing IDs; if they remain stale, allow one reload and recheck. Record partial coverage when freshness cannot be established.

Open candidates through their visible result-card links when available. Use the exact observed href for navigation and the canonical URL for saved identity. Check the settled destination URL and rendered listing details. If direct navigation ends on the homepage without an access challenge, return to the source results and try the actual card link once. Record the source link, navigation method, destination and any sign-in/access prompt. If details remain inaccessible, retain card evidence with unverified details and describe the observed navigation; its cause, item availability and suitability remain unknown. Stop on explicit access challenges.

Search terms do not enforce hard requirements. Use observed native filters where available, then check each candidate's model, year, transmission, brand or size against the brief. Recheck category and radius after submitting a new query; sites can reset them. Keep local results separate from explicitly extended-area or suggested results, and record any unverified filter application in coverage.

1. Read `get_goodfinds_search_context({search_id})` for the assigned brief; the returned `search_runs` includes its runs. The context tool does not accept `run_id`. Use the requested run ID and claim it with `claim_goodfinds_search_run` using your actual runtime agent identity and a fresh worker ID. Reuse a run already owned by you. If the supplied run is cancelled, fulfilled or belongs to a changed brief, record the interruption and return to the parent. Use the latest returned run version as `expected_version`; read progress when that version is unavailable or a conflict occurs.
2. Resolve a pending [search cover](search-covers.md) first, using its bounded model/family selection path. Then read query_plans.excluded_models and saved feedback before searching. Follow returned queries, which omit explicitly excluded models and documented aliases. Skip matching excluded search cards before deep inspection; retain category queries and do not suppress unknown models by title alone. For a precise model brief, start with one exact query per accepted model and one broad category query. Add aliases or broader terms when results leave a coverage gap; account for skipped redundant queries with a reason. Keep reference_model to one actual model; a phrase joining models with “or” belongs in the title, with each model in query_plan. Persist category_terms, query_plan and documented model_aliases in discovery. For espresso, include “coffee machine” and “espresso machine” early. Do not narrow every category query to the reference brand. Run a broad query before detailed seller/profile/photo work. Broad results still undergo exact-model and must-have rules.
3. On every scheduled run, first complete the [saved-listing availability pass](availability-checks.md). Then discover with search cards/title/visible full price and canonical IDs first. Import after each query with a fresh batch `request_id` (reuse its ID and exact arguments on retry), `run_id`, the claimed `worker_id` and `collection_stage: discovery`. Save visible thumbnails using [listing media capture](listing-evidence.md#capture-photos-and-videos-for-saved-listings). Record visible fields, incomplete image_review/video_review and unknown details. After provisional imports, read `list_goodfinds_media_repairs` for this search and capture ready photo/video galleries; do not restrict media saving to the shortlist. Save recovery through `attach_goodfinds_listing_media`, including partial/unavailable outcomes and the actual capture time. Resume missing media from earlier runs without changing old fact timestamps or their verification. Repeated sightings retain detailed evidence but require a fresh detail check before an alert. Do not guess setup costs, condition or gallery contents.
4. Update through `update_goodfinds_search_run`: `request: {run_id, worker_id, expected_version, query: <full returned query with updated status/counts>, phase, next_step}`. Record result_count and unique_relevant_count when known; deduplicate IDs across queries. Skipped/failed queries need a reason. Unknown count stays null. Newly discovered queries use add_queries with unique IDs, planned status and a selected marketplace.
5. Use the saved hard requirements and returned assessments to select a provisional shortlist for evidence collection. Buying judgment and product-tradeoff research stay in the buying chat under [worker model routing](state-model.md#worker-model-routing). Verify every gallery image and video, model identity, functioning, condition and model-specific essential accessories against the saved checks. Persist expected discovery.verification_checks as `{id, label, question}`. For manual espresso, check the correct portafilter, usable baskets and tamper; return model-specific research or ambiguous accessories to the buying chat. An integrated grinder may remove a separate grinder cost. A tidy photo does not establish a complete package.
6. Import details with `collection_stage: verification`, complete/partial image_review, video_review, media_capture and verification_checks. Source every confirmed or explicitly missing fact. Track required extras as setup_costs labelled observed/estimate/unknown, with currency and source. A missing part may be acceptable if replacements are allowed and the full setup fits. An unknown part remains a potential clarification, not a presumed replacement charge. Select seller questions through [message wording by stage](seller-conversations.md#message-wording-by-stage); retain the full checklist internally. Keep asking-price peers model-specific.
7. Confirm the early [search cover](search-covers.md) attempt attached the image or recorded a concrete blocker. Reuse its outcome; another attempt is useful only if new source evidence resolves the blocker. Optional seller/profile/avatar enrichment gets one bounded attempt (about 10 seconds per download, 30 seconds total per listing). Failure retains unknown metadata and a note. Required seller-count limits still need evidence before final eligibility. Stop on access challenges and record the interruption.
8. Before final ranking or completion, run the [journey enrichment pass](journeys.md) for relevant saved listings with a travel requirement. Resolve each pending town with a cached or observed route, or record the specific access/location interruption. A visible town with no check is pending enrichment, not an unknown location. Set verifying for the shortlist, then completed only after all queries are completed or explicitly skipped and a broad category query succeeded. Completed query coverage does not mean exhaustive inventory: search_runs.pagination_complete remains independently truthful. Use partial/blocked with a next step for interruptions. Resume with saved outcomes and listing keys. Cancellation preserves saved listings and prevents further imports.

9. Read `list_goodfinds_next_steps` after completed/partial status. Collection workers return saved candidates, unresolved checks and prepared next steps to the buying chat. The buying chat compares candidates and presents the recommendation and saved exact opening message with review/send, choose another and keep searching choices. Continue through [buying follow-through](buying-follow-through.md), including chat when the panel is unavailable. Draft preparation is automatic and does not send anything.
10. Resolve the returned monitoring.next_action through [evaluation and delivery](evaluation-delivery.md). Reuse the buyer's established monitoring choice. If it remains undecided, offer search once versus keep watching after presenting the useful results. New searches default to recurring monitoring. Recurring setup is complete only with a verified host receipt or an explained scheduling interruption; explicit one-off choices remain authoritative.

Use `workflow.actions` and the generated [run states and guards](state-model.md#search-runs) to select or recover the next lifecycle step. Read views from `search_run_workflows[run_id]`. Descriptors identify actions that still require inputs. Satisfy the returned blockers and conditions; they grant no browser or sending permission. Keep one scoped brief in context; page summaries and fetch rich evidence on demand. Imports increment the run version: use the returned version, rereading compact runs only if absent or conflicting. Maintain lease activity at least once a minute and before lengthy work; check cancellation before every browser step and import. The panel searches for new scheduled runs even while idle, refreshes active work more often and pauses polling when hidden. Report query coverage, unique leads, unresolved checks and next step; routine reload instructions are unnecessary.
