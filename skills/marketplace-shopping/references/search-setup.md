# Search setup

1. Read `get_goodfinds_workspace` and `list_goodfinds_search_templates`. For every item, follow [adaptive interviews](adaptive-interviews.md): extract the brief, use the host's built-in web search to research relevant buying decisions, and adapt a starter or generate a definition using the supported field contract. If the item or budget basis is ambiguous, resolve that ambiguity first. Consult [buyer interviews](buyer-interviews.md) when its category examples apply. Keep the category and field IDs stable. This step is complete when sourced research supports the relevant distinctions and the supplied answers are preserved.
2. Apply the question-design check below. Choose the highest-value missing setup details, aiming for 1–3 follow-ups and at most 5 before offering review or further questions. A precise brief can need zero questions. Mark low-impact optional questions `question_stage: refinement`; mark an optional but decisive setup question `question_stage: setup`. Required answers always belong in setup. Preserve every stated requirement even when it belongs to a refinement field; the stage controls when to ask, not whether to match it. If more than five indispensable answers are missing, preserve the draft and offer to continue rather than dropping requirements or inventing answers.
3. Save the definition and partial answers with `save_goodfinds_search_draft`, passing the current revision. Resume an existing matching draft instead of creating a duplicate. A draft is unfinished work and does not enable searching.
4. Call `ask_goodfinds_search_question` with its draft ID and `stage: setup`. It asks only unanswered applicable setup questions, in definition order; put decisive questions first. Reassess the plan after each answer following the adaptive-interview guide, then repeat while status is `answered`, within the question budget. On `cancelled` or `declined`, preserve the draft and stop. On `unsupported`, use the same short setup sequence in chat or the panel. Record explicit no preference as null; leave unasked optional fields absent. Reuse a saved location, collection limit or other answer only when it applies to this search, and show that reuse in the review.
5. When `ready`, save the brief within the user’s requested scope and show an editable recap. If the user asked to find an item now, start searching without another save/search approval question. Offer optional refinement after useful results arrive. `ready` means setup is complete; it does not require answers to every optional field. If the user wants more detail, select the relevant refinement dimensions and call `ask_goodfinds_search_question` with `stage: refinement` and their IDs in `refinement_fields`, or update the draft from their chat answer. Omitting `refinement_fields` asks all applicable refinements, so reserve that for a request for all details. Save established requirements with `save_goodfinds_search`, including `draft_id` and the latest revision. Successful save removes the draft; cancellation leaves it resumable.
6. Resolve monitoring through [evaluation and delivery](evaluation-delivery.md). Reuse explicit one-off or recurring-monitoring instructions and saved monitoring preferences. When undecided, deliver the initial results first and offer search once versus keep watching; this choice must not delay the initial search. An explicit recurring-monitoring request authorizes completing host scheduling after live access is validated. Completion includes the saved criteria and an honest monitoring outcome, rather than an implied schedule from an hourly preference.

**Search names:** Use a short product, model or category name for draft `name`, saved search `name` and `definition.title`: for example, “Ninja Crispi DualZone” or “Coffee machine”. Keep budgets and price ranges in the matching answers under `values`, where the panel displays them as search details. A budget edit keeps the product name stable. Retain numbers that identify a model or generation, such as “Ninja AF400UK” or “iPhone 15”. Preserve a custom name only when the buyer explicitly asks for that label; a price mentioned in the buying brief is a criterion. Before saving, check that the generated name identifies the item and the price constraint remains in its own answer.

For edits, load the saved definition and answers. Changing values preserves its definition; changing fields or matching semantics requires an increased `definition.version`. Keep configuration and listing history outside the installed plugin directory.

Use the panel’s immediate category illustration while saving the brief and starting discovery. After the initial discovery pass, complete the required automatic [search card image follow-up](search-covers.md) for identifiable products: fetch a suitable manufacturer photo, cache it locally and attach it with `set_goodfinds_search_cover`, reusing a suitable photo already saved in the user's workspace. Resolve returned cover_follow_up before finishing, including when no listings were found. The plugin includes neutral or regional rental illustrations and reusable artwork for common marketplace item types. MacBook Pro, Mac mini and Mac Pro photos are fetched into the user's workspace, just like other identified products; generic illustrations do not complete their photo follow-up. Search covers represent the brief; actual listing photos remain the evidence for items available to buy or rent.

**Question-design check:** Each question must collect a distinct fact or preference. Compare the meaning of every proposed question with the user's brief and the other questions, including differently worded questions. Merge or remove questions that collect the same information, and reuse information already established by an answer. For example, whole property/private room/shared room already describes the rental arrangement; keep that choice and omit a second shared/not-shared question. Add a follow-up only when it resolves an independent detail that remains unknown, and use a visibility condition when it applies to only some answers. The check is complete when every remaining question adds information needed to match listings or compare prices.

Prioritize questions that prevent unusable results: item identity or purpose, budget basis, fit/compatibility and purchase/collection viability. Marketplace filters are a vocabulary reference, not a questionnaire to copy. Treat site-specific categories as discovery hints; retain observable buyer-led attributes outside those filters as typed matching fields with evidence keys. Use multiple choice for a small, meaningful set of alternatives, no preference for optional criteria, numeric custom values and text for unbounded details. Keep the user's sizing system and units. Clarify only ambiguity that changes the search. Separate must-haves from nice-to-haves, and show assumptions in review rather than making agent suggestions into hard filters. Seller facts such as history, damage or battery health are evidence to collect; ask buyers about acceptance thresholds only when relevant. On scarce results, explain which criterion limits the search and get the user's choice before relaxing it.

Definitions use schema version 1, supported controls, earlier-field visibility conditions, deterministic matching operators, and explicit required/preferred rules. Generate data rather than executable UI code. Use separate dimensions for house/flat, whole property/private room/shared room, bedrooms, and floor preference. Ask whether an ambiguous room count means bedrooms. Use `price_minor` for budgets, integer pence for saved prices, and `display_divisor: 100` to show pounds. Rental prices have an explicit month/week period; normalize observed rents only with recorded evidence. Match areas using consistent normalized names. Choose comparison attributes for the category rather than reusing laptop dimensions.

Default to the in-app browser. The in-app browser has its own sign-in session. Use the external browser only when selected by the user. Resolve an ambiguous origin before evaluating live journey times. Treat a stated storage capacity as a minimum unless the user requests an exact capacity; make that interpretation visible in the search summary.

The prototype uses a 30-day comparison window and requires three other comparable listings. Offer these as adjustable settings. Use the arithmetic average, as requested by the user. The candidate is excluded from its own reference average. Use the saved definition’s exact comparison attributes. Laptop starters compare product, chip, RAM, SSD, laptop screen size, new/used/refurbished state and condition; rental starters compare area, accommodation, property type and bedrooms within the same currency and rent period. Keep over-budget listings in the comparison pool. A seller-listing-count limit filters candidates, not price-comparison peers. When requested, add a whole-number range matched to `seller_listing_count` to any category; it is an optional refinement with a hard requirement when answered. Leave either bound blank for an open-ended limit. Unknown or stale counts need review; partial totals can prove a minimum but cannot prove a maximum. Preserve the rest of the saved definition and increase its version when adding this field.
