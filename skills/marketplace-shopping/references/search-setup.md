# Search setup

1. Check the host capabilities described in the skill. Read `get_goodfinds_setup_context` before asking questions, passing the product category and explicit regional choices in `preferences` when known. Supply available client locale/country as `hints` only when the host has not supplied metadata; leave absent hints unknown. It combines settings, scoped revisions, a compact search/draft index and a starter template in the resolved currency. Use `regional_context` as described below. For a matching saved search, read `get_goodfinds_search_context` with its ID; reuse a matching draft. Open the panel separately when useful. Setup does not need a full workspace snapshot or the entire template catalog.
2. Extract every supplied requirement into typed fields and `values`. A precise brief needs zero questions. Accept the latest stated city, area or postcode; if it differs from settings, save only `{origin: "the stated place", location: null}` with `revisions.settings`. Treat a city as sufficient and describe city-centre routing as an approximation in the recap. The buyer can change it later. Ask only when the place itself is ambiguous, not merely broad. Keep driving-time uncertainty visible near the limit.
3. For a complete brief, call `save_goodfinds_search` directly with a JSON `search` object, `expected_entity_revision: revisions.absent` for a new search (or `revisions.searches[id]` for an edit), and a stable UUID `request_id`. New searches default to recurring monitoring at the saved cadence, two hours in a new workspace. Supply `initial_monitoring: {preference: "once"}` for an explicit one-off request, or `recurring` with the requested `interval_minutes` or `timing`. Existing search edits preserve monitoring; use `set_goodfinds_monitoring` for an explicit change. Verify the returned saved search contains the stated matching requirements; another read is unnecessary when the save result supplies them.
4. If consequential answers are missing, follow [adaptive interviews](adaptive-interviews.md) and the question-design check below. Batch independent choices into one short question, at most five setup follow-ups. Use a draft only to preserve unfinished work. For native interviews, `ask_goodfinds_search_question` asks unanswered applicable setup fields. Keep optional refinements for later. Cancellation preserves the draft. Promote with `draft_id` and `expected_draft_revision: revisions.drafts[draft_id]`; the destination search still uses its own entity revision. See [tool contracts](tool-contracts.md).
5. Show an editable recap and dispatch through [background work](background-work.md). A complete brief needs no question tool, save/search confirmation or preliminary exhaustive product research. Research unknown identity, compatibility or acceptance facts when they affect the next step; other buying evidence belongs in collection. Keep storage, colour and other unstated preferences unrestricted.
6. Complete [scheduling and verification](evaluation-delivery.md#scheduling-and-verification) in this buying chat. Inform the buyer of the two-hour default in the recap, without adding a monitoring-choice gate. Verify the host schedule or state the concrete scheduling blocker. A saved recurring preference alone is not active monitoring. Preserve explicit one-off choices, custom timing, existing pauses and quiet hours.

## Regional defaults

For a named model, pass its product category to setup: both a Golf GTI and a Toyota Camry use `category: vehicle`. The model's country of origin does not select the shopping market. Use the resolved shopping country and the returned ranked marketplaces: US vehicle searches start with CarGurus US, Cars.com and Autotrader US, with Facebook and other eligible sources; UK searches use Auto Trader UK with their other eligible sources. State those returned names in the recap. Keep the requested model unchanged; regional product substitutions belong to illustrative website examples, not the buyer's brief.

Resolve shopping country, language, budget currency and collection/delivery independently. `regional_context` applies explicit `preferences`, then saved `regional_preferences`, then saved location and available hints. An explicit `€500` is EUR 500 and `£500` is GBP 500, even abroad; pass that currency in `preferences.currency`. For bare `500`, use the resolved currency and show it in the recap. `$` needs the relevant dollar currency; when saved/search context does not resolve it, ask once. Language-only `en` and timezone alone do not establish a country. Client hints suggest a shopping market, never a confirmed collection origin.

Use the returned currency-adjusted template. When currency is unresolved, `templates` is empty: resolve only the consequential missing country/currency, then read the matching starter. A supplied city is enough for collection; delivery may need only country/postal area. Preserve saved searches and drafts, including their price currency and selected marketplaces, unless the buyer changes them. A detected travel locale does not replace saved preferences. Save persistent regional defaults only when the buyer chooses them, through `save_goodfinds_settings.settings.regional_preferences`; omitted fields preserve other defaults and `null` clears an individual default.

For new briefs, save the resolved `country`, `locale` and `fulfilment` in `search.market` (or `draft.market`), and the price currency in `definition.price.currency`. Copy the recommended IDs from `regional_context.marketplaces` unless the buyer selected sources explicitly. Recommendations use country, category, fulfilment and disabled-platform preferences. A new save can supply defaults from saved settings when marketplaces are omitted; edits preserve their existing choices. Use `marketplace_routes[search_id]` from search context for browsing selected regional sites. A null route means no supported variant: report it, rather than substituting a UK site or rewriting a listing URL. Keep delivery eligibility and total costs as listing-level evidence; selecting a regional site alone does not prove either.

**No preference:** An explicit “no price limit” is a complete answer. Set that definition field's `required` to `false` and store `values.max_price_minor: null`; keep its matching rule so a later budget works. Increase the definition version when changing an existing definition. An aspirational price belongs in the recap or a preferred rule, not a hard filter. Never substitute a large numeric ceiling. Apply the same adaptation to other explicit no-preference answers. For example, a 14-inch MacBook Pro brief can preserve M3+, 24 GB, 1 TB and used-only criteria while leaving price unbounded. Use the template's capacity units (1 TB is 1000 GB), and preserve the screen-size and item-state requirements as typed matching fields.

**Search names:** Use a short product, model or category name for draft `name`, saved search `name` and `definition.title`: for example, “Ninja Crispi DualZone” or “Coffee machine”. Keep budgets and price ranges in the matching answers under `values`, where the panel displays them as search details. A budget edit keeps the product name stable. Retain numbers that identify a model or generation, such as “Ninja AF400UK” or “iPhone 15”. Preserve a custom name only when the buyer explicitly asks for that label; a price mentioned in the buying brief is a criterion. Before saving, check that the generated name identifies the item and the price constraint remains in its own answer.

**Model identity:** For `discovery.scope: exact`, use the same model identity in `reference_model`, the matching field and observed `attributes[model_attribute]`. For a Ford Focus, keep make `Ford` separate from model `Focus`; the query can still say “Ford Focus 2018 automatic”. Use documented aliases for equivalent model names. A brand/category brief such as a J.Crew hoodie has no named model: use `scope: alternatives` without `reference_model`, then enforce brand, item type, pattern and size through required matching fields. This preserves every must-have without adding an unanswerable model check.

For edits, load the saved definition and answers. Changing values preserves its definition; changing fields or matching semantics requires an increased `definition.version`. Keep configuration and listing history outside the installed plugin directory.

Use the panel’s immediate category illustration while saving the brief and starting discovery. Make the required automatic [search card image follow-up](search-covers.md) the worker’s first bounded media task for identifiable products, before marketplace discovery: fetch a suitable manufacturer photo, cache it locally and attach it with `set_goodfinds_search_cover`, reusing a suitable photo already saved in the user's workspace. Resolve returned cover_follow_up before finishing, including when no listings were found. The plugin includes neutral or regional rental illustrations and reusable artwork for common marketplace item types. MacBook Pro, Mac mini and Mac Pro photos are fetched into the user's workspace, just like other identified products; generic illustrations do not complete their photo follow-up. Search covers represent the brief; actual listing photos remain the evidence for items available to buy or rent.

**Question-design check:** Before saving, map each stated must-have to a typed matching field and saved answer. Description text and comparison attributes alone do not filter listings. Item state (new/used/refurbished) and condition grade are separate requirements. Check those mappings in the save response before reporting completion. Each question must collect a distinct fact or preference. Compare the meaning of every proposed question with the user's brief and the other questions, including differently worded questions. Merge or remove questions that collect the same information, and reuse information already established by an answer. For example, whole property/private room/shared room already describes the rental arrangement; keep that choice and omit a second shared/not-shared question. Add a follow-up only when it resolves an independent detail that remains unknown, and use a visibility condition when it applies to only some answers. The check is complete when every remaining question adds information needed to match listings or compare prices.

Prioritize questions that prevent unusable results: item identity or purpose, budget basis, fit/compatibility and purchase/collection viability. Marketplace filters are a vocabulary reference, not a questionnaire to copy. Treat site-specific categories as discovery hints; retain observable buyer-led attributes outside those filters as typed matching fields with evidence keys. Use multiple choice for a small, meaningful set of alternatives, no preference for optional criteria, numeric custom values and text for unbounded details. Keep the user's sizing system and units. Clarify only ambiguity that changes the search. Separate must-haves from nice-to-haves, and show assumptions in review rather than making agent suggestions into hard filters. Seller facts such as history, damage or battery health are evidence to collect; ask buyers about acceptance thresholds only when relevant. On scarce results, explain which criterion limits the search and get the user's choice before relaxing it.

Definitions use schema version 1, supported controls, earlier-field visibility conditions, deterministic matching operators, and explicit required/preferred rules. Generate data rather than executable UI code. Use separate dimensions for house/flat, whole property/private room/shared room, bedrooms, and floor preference. Ask whether an ambiguous room count means bedrooms. Use `price_minor` for budgets, integer minor units in the explicit price currency. Use the template’s `display_divisor` (100 for GBP/USD/EUR, 1 for JPY, 1000 for three-decimal currencies). Rental prices have an explicit month/week period; normalize observed rents only with recorded evidence. Match areas using consistent normalized names. Choose comparison attributes for the category rather than reusing laptop dimensions.

Default to the in-app browser. The in-app browser has its own sign-in session. Use the external browser only when selected by the user. Resolve an ambiguous origin before evaluating live journey times. Treat a stated storage capacity as a minimum unless the user requests an exact capacity; make that interpretation visible in the search summary.

Goodfinds defaults to a 30-day comparison window and requires three other comparable listings. Offer these as adjustable settings. Use the arithmetic average. The candidate is excluded from its own reference average. Use the saved definition’s exact comparison attributes. Laptop starters compare product, chip, RAM, SSD, laptop screen size, new/used/refurbished state and condition; rental starters compare area, accommodation, property type and bedrooms within the same currency and rent period. Keep over-budget listings in the comparison pool. A seller-listing-count limit filters candidates, not price-comparison peers. When requested, add a whole-number range matched to `seller_listing_count` to any category; it is an optional refinement with a hard requirement when answered. Leave either bound blank for an open-ended limit. Unknown or stale counts need review; partial totals can prove a minimum but cannot prove a maximum. Preserve the rest of the saved definition and increase its version when adding this field.
