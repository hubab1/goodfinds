# Edits, retries and workflow results

Read `get_goodfinds_setup_context` for setup, or a scoped `get_goodfinds_search_context`/`get_goodfinds_settings` before editing. Inspect the advertised input schema before constructing an unfamiliar mutation. If a nested object omits its fields, read `get_goodfinds_tool_schema({name: "TOOL"})` once for its complete contract; reuse returned setup templates when available. The packaged fallback also provides `goodfinds schema TOOL`. Validate all required fields together; empty calls are not schema discovery. Use the `revisions` map, not the top-level `revision` (a workspace snapshot). Copy the token for the entity the tool changes:

| Action                                  | `expected_entity_revision`                                                    | Additional token                                      |
| --------------------------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------- |
| Create a search or draft                | `revisions.absent`                                                            | None                                                  |
| Edit a search                           | `revisions.searches[search_id]`                                               | None                                                  |
| Resume a draft                          | `revisions.drafts[draft_id]`                                                  | None                                                  |
| Promote a draft to a new search         | `revisions.absent`                                                            | `expected_draft_revision: revisions.drafts[draft_id]` |
| Promote a draft into an existing search | `revisions.searches[search_id]`                                               | `expected_draft_revision: revisions.drafts[draft_id]` |
| Change settings                         | `revisions.settings`                                                          | None                                                  |
| Change monitoring, feedback or evidence | Matching `monitoring[search_id]`, `feedback[feedback_id]` or `evidence` token | None                                                  |

A retained deleted identity uses its own token instead of `revisions.absent`. Pass `search` and `draft` as JSON objects, with answers nested under `values`. A completed brief needs only `save_goodfinds_search`; drafts preserve unfinished interviews. New searches save recurring monitoring at the saved cadence (two hours by default); `initial_monitoring` applies an explicit one-off or custom timing choice atomically at creation. Edits preserve monitoring. `request_goodfinds_search_run` requires its UUID inside `request: {search_id, trigger: "manual", request_id}`; the outer mutation receipt UUID does not replace it. Consume `search_run` from its result. For model-facing output, read `structuredContent` or text once and omit the full app-only `_meta` snapshot. The server accepts one spelling of each argument and one current contract.

A revision conflict returns `error.resource`, `error.current_revision` and `error.recovery` in both text and structured output. It means the supplied token does not match that resource; it does not prove someone changed the workspace. Reread that resource, reconcile the intended edit with newer data and retry. Continue automatically when the changes affect independent resources. Ask the buyer only when their intended result conflicts with a newer edit or an unresolved buying decision. Never resubmit a stale complete document over newer values. Correct an identified argument mistake and retry automatically. If the same failure remains after a fresh read and one corrected retry, preserve the draft and report the exact resource/error and the blocked step. Do not swap tokens speculatively, ask the buyer to approve each retry, or edit the database to bypass the contract. Read-only diagnostics within this task need no extra conversational permission; host permissions still apply.

Give each import batch and configuration mutation a fresh `request_id` UUID. If the response is lost, retry the same ID with exactly the original arguments. Reusing the ID for different arguments fails validation. `receipt.replayed` identifies a retry: the operation result is the original committed result, while the panel receives a fresh snapshot. Successful imports return `import_receipt.evaluation_id` and the current search run. A scheduled import stopped by a timing guard returns `import_receipt: null` with `scheduled_check`; it saves no observations. After a successful result, use its new resource revisions for the next edit.

`search` is a definition plus its answers; `search_id` identifies it. A `run_id` identifies one execution of that search and `worker_id` identifies its current lease owner. Choose the displaying or non-displaying queue tool through [panel handoff](panel-chat-actions.md#show-the-search-at-the-right-time), then use `claim_goodfinds_search_run` in the actual executor. A direct single-platform search may execute in the buying chat; delegated work claims in the assigned worker. Background and scheduled queues use `request_goodfinds_search_run`. Keep the supplied manual or scheduled trigger. The worker renews its lease and records query progress, observations and interruptions using the returned allowed actions.

Search and seller results include `workflow.actions`: event, canonical operation/tool, availability (`available`, `requires_input`, `blocked`), required inputs, conditions and stable blocker codes. Search context and progress reads expose `search_run_workflows[run_id]`; context also exposes `search_workflows[search_id]`. `get_goodfinds_listing` accepts optional `search_id` and returns an independent listing workflow with scoped assessments. See the generated [state reference](state-model.md). Mutation errors carry the same guard blockers when a lifecycle guard rejects an action. Actual browser access and agent identity come from observed host capabilities. Workflow results do not authorize sending: each outgoing message still requires the buyer's exact reviewed action and a fresh, single-use `execution.send_permitted: true` from `issue_goodfinds_message_send_permit`.

Use returned compact resources for follow-up decisions. Page listing summaries and fetch complete evidence for the shortlisted item. Read-only tools never create runs or enable monitoring. Sample mode is an isolated fictional workspace; it cannot establish live access, seller evidence or real schedules.

## Confirm committed work

Only describe a mutation as saved after a successful tool result with its returned resource. Seller draft saves return `mutation_receipt` with listing key, version, draft hash and commit time; retain it in the completion record. Omit `responds_to` only for a new enquiry (defaults to null); for a reply copy the actual incoming message ID. Saving never permits sending. If a call fails, correct it or report the unsaved draft; proposed text in chat is not a persisted draft. For audits, count failures from actual host/tool records, including recovered failures; do not infer zero errors from a successful final state. Report unavailable counts as unknown.

Cover edits and research summary/source/date edits preserve execution. Research queries, candidate model identities, matching rules and buyer answers remain execution inputs: finish research before starting, or deliberately start a replacement run after those change. A claim returning a requested run without your worker is a capacity wait, not permission to browse.

## Delete all workspace data

A request to delete searches alone uses search removal and preserves history. An explicit full-data reset uses `preview_goodfinds_workspace_reset`. Retain buying briefs in the chat first if requested. Show the scope/counts; the user's existing explicit reset request authorizes the deletion. Stop the listed active runs and close their task tabs, delete only the listed Goodfinds host schedules using the host automation tool, then preview again. Never edit automation files directly. Pass the new reset_token, a fresh request_id and confirmation `delete_all_goodfinds_data` to `reset_goodfinds_workspace`. A stale preview requires a fresh preview. Check the successful reset receipt and `media_cleanup_complete`; if false retry the same ID/arguments to finish file cleanup without deleting subsequently added data. The operation resets settings, conversations, run history, connection observations and cached media in that workspace; browser sign-ins, plugin installation, other workspaces and chats stay intact. An unreadable host schedule must be resolved through the host before reset.

## Journey checks

Use `list_goodfinds_journey_checks({search_id?, offset?, limit?})` for a town-grouped queue. It returns `origin_key`, `enabled`, `origin_confirmed`, `checks`, `total` and `next_offset`. Open each returned maps_url in the selected browser and save `record_goodfinds_journey_check({request_id?, report})`. Report contains `origin_key`, `destination`, `country` (nullable), `listing_keys`, `drive_minutes`, `precision: "town"`, `estimate_kind: "traffic" | "typical"`, `source_url`, `evidence` and actual `checked_at`. No listing import or refreshed observation time is needed. Use the same request ID and payload when retrying a write. See [journey checks](journeys.md) for freshness, approximate results and blocked routes.

`get_goodfinds_search_context` returns arrays: `searches` and `search_runs` use `id`, while `query_plans` uses `search_id`. Select from those arrays; do not treat them as ID-keyed objects. Use the latest mutation result before issuing another read. Generate request UUIDs with the host’s supported facility; a JavaScript orchestration sandbox may not expose `crypto`.
