# Edits, retries and workflow results

Read `get_goodfinds_search_context` or `get_goodfinds_settings` before editing. Supply `expected_entity_revision` from `revisions.searches[search_id]`, `drafts[draft_id]`, `monitoring[search_id]`, `feedback[feedback_id]`, `settings` or `evidence`, matching the resource changed by the tool. A new identity uses `revisions.absent`; a retained deleted identity has its own token. Promoting a draft also supplies `expected_draft_revision`. The server accepts one spelling of each argument and one current contract.

A revision conflict returns the resource and its current revision. Reread that resource, reconcile the intended edit with newer data and retry. Continue automatically when the changes affect independent resources. Ask the buyer only when their intended result conflicts with a newer edit or an unresolved buying decision. Never resubmit a stale complete document over newer values.

Give each import batch and configuration mutation a fresh `request_id` UUID. If the response is lost, retry the same ID with exactly the original arguments. Reusing the ID for different arguments fails validation. `receipt.replayed` identifies a retry: the operation result is the original committed result, while the panel receives a fresh snapshot. Imports return `import_receipt.evaluation_id` and the current search run. After a successful result, use its new resource revisions for the next edit.

`search` is a definition plus its answers; `search_id` identifies it. A `run_id` identifies one execution of that search and `worker_id` identifies its current lease owner. Use `request_goodfinds_search_run` in the parent conversation, then `claim_goodfinds_search_run` in the assigned worker. Keep the supplied manual or scheduled trigger. The worker renews its lease and records query progress, observations and interruptions using the returned allowed actions.

Search and seller results include `workflow.actions`: event, canonical operation/tool, availability (`available`, `requires_input`, `blocked`), required inputs, conditions and stable blocker codes. Search context and progress reads expose `search_run_workflows[run_id]`; context also exposes `search_workflows[search_id]`. `get_goodfinds_listing` accepts optional `search_id` and returns an independent listing workflow with scoped assessments. See the generated [state reference](state-model.md). `allowed_actions` remains a compatibility list of proposed tools, including tools needing inputs. Mutation errors carry the same guard blockers when a lifecycle guard rejects an action. Actual browser access and agent identity come from observed host capabilities. Workflow results do not authorize sending: each outgoing message still requires the buyer's exact reviewed action and a fresh, single-use `execution.send_permitted: true` from `issue_goodfinds_message_send_permit`.

Use returned compact resources for follow-up decisions. Page listing summaries and fetch complete evidence for the shortlisted item. Read-only tools never create runs or enable monitoring. Sample mode is an isolated fictional workspace; it cannot establish live access, seller evidence or real schedules.

## Journey checks

Use `list_goodfinds_journey_checks({search_id?, offset?, limit?})` for a town-grouped queue. It returns `origin_key`, `enabled`, `origin_confirmed`, `checks`, `total` and `next_offset`. Open each returned maps_url in the selected browser and save `record_goodfinds_journey_check({request_id?, report})`. Report contains `origin_key`, `destination`, `country` (nullable), `listing_keys`, `drive_minutes`, `precision: "town"`, `estimate_kind: "traffic" | "typical"`, `source_url`, `evidence` and actual `checked_at`. No listing import or refreshed observation time is needed. Use the same request ID and payload when retrying a write. See [journey checks](journeys.md) for freshness, approximate results and blocked routes.
