# Listing evidence and local media

## Quiet visual inspection

Read the browser tool's documentation before choosing capture options. Use text/DOM/accessibility reads for search cards, descriptions, profile metadata and messaging controls. Avoid combined state-and-screenshot calls when text is sufficient. Use documented non-emitting capture/download options when they retain access to the evidence needed for inspection. A hidden capture or downloaded file alone does not establish that the image was reviewed.

For required photo inspection, use the host's supported visual-reading path. If it necessarily displays an image tool result in chat, inspect with the minimum needed captures and record truthful gallery coverage. Do not emit the image again, forward screenshot content blocks from orchestration tools, or attach a screenshot as progress or final proof unless the buyer asks for it. Goodfinds cannot override another host tool's renderer or promise all visual results are invisible. Keep the final response focused on candidates, prices, evidence, unresolved checks and next steps; saved listing photos remain available in the panel.

## Capture photos and videos for saved listings

Saving media is part of collection for every saved listing, separate from deep shortlist verification. During discovery, download the visible listing thumbnail before importing when available. Cache it with `cache_goodfinds_media` and attach its image ordinal through `photos`. Do not cache search page screenshots as product photos.

After the first provisional imports, make a media pass over newly saved listings and previously saved listings missing media. Open each listing once, traverse its gallery, and download every available original photo and seller video through the host browser's documented media download or visible download controls. Use observed media elements/assets, not guessed CDN addresses. After each gallery navigation, confirm the displayed ordinal and loaded source before downloading; do not repeatedly save the lead image under different positions. Cache photos and videos with `cache_goodfinds_media`: up to 20 files/100 MB per batch, 10 MB per photo, 50 MB per video. Split batches; isolate individual failures so one inaccessible video does not discard other downloaded photos. Reuse existing content IDs. Keep broad discovery moving and save progress incrementally so an interrupted pass can resume from missing media.

While that detail page is open, expand and read the full listing description, even when the asking price already rules the item out. Save freshly observed price, location, seller name/profile link, description and specifications through `import_goodfinds_listing_observations`, with structured values and source excerpts: for example, “512 GB storage and 16 GB ram” supplies `ssd_gb: 512` and `ram_gb: 16`. Include the price basis on every priced observation as specified in [the observation contract](observations.md#price-basis-and-payment-methods). Read back the supplied fields before leaving the item; a successful receipt alone does not establish that every field was retained. Record hidden or unavailable details explicitly rather than copying old facts with a fresh timestamp. Keep partially checked items at `collection_stage: discovery`; reading a description does not establish working condition or complete gallery review. A media receipt alone cannot save description/specification facts. For an explicit media-only repair, preserve old fact timestamps unless fresh facts were actually read, then save those separately as a new observation.

Read `list_goodfinds_media_repairs` scoped to the search before the media pass. It includes older galleries with photos but unconfirmed video capture. During automatic searches, process ready entries and respect retry times; an explicit media-reconciliation request can retry sooner. For an existing listing, save cached files with `attach_goodfinds_listing_media`: `listing_key`, optional `photos`/`videos`, and `media_capture` with the actual `captured_at`. This records a separate durable media receipt. Do not re-import old listing facts as a new observation, change their check timestamps, or mark media reviewed just because it downloaded. Complete capture explicitly supplies both arrays and observed totals; partial/unavailable preserves earlier files. Re-read the queue to verify saved results. If the running chat lacks these updated tools, use the bundled protocol helper from connection diagnostics rather than asking the buyer to paste requests.

Limit video capture to the seller's listing gallery. Marketplace detail pages can contain advertisement videos below the gallery; these do not belong to the listing and must not be downloaded or counted.

After selecting a video thumbnail, wait for that gallery video's loaded `src`/`currentSrc` before downloading. A visible video node can initially have an empty source; that loading state is not a failed download. Use a bounded supported browser wait for the selected element, confirm it is in the gallery before the listing heading, and then download it. Do not fall through to a loaded advertisement video elsewhere on the page.

A single-photo listing may have no gallery navigation buttons and omit explicit image width/height attributes. Facebook can put a visibly loaded product image inside `aria-hidden="true"`; that image is absent from accessibility snapshots and role-based image locators. A missing `getByRole('img')` match is therefore not evidence of a missing photo. Inspect actual gallery DOM `img` elements, their observed alt text, loaded `currentSrc`/`src`, `complete`, natural dimensions and displayed bounds. With a documented locator API, use an observed selector such as `img[alt="Product photo of …"]` and a bounded wait, then download that actual element. Select the displayed full-size image, not a thumbnail with the same alt text. Use a screenshot when DOM state alone cannot establish the displayed gallery. Save a loaded single image as photo 1. A listing heading can appear before its gallery finishes loading; use a bounded gallery wait before recording a failure. If Facebook explicitly says the listing is no longer available, record that reason rather than a generic selector timeout.

Import `photos: [{media_id, position, caption}]` and `videos: [{media_id, position, caption, poster_media_id?}]`. Photo and video ordinals are separate positive sequences. A poster is optional and must be an actual observed image cached separately. `media_capture` records `status: complete|partial|unavailable`, observed `expected_photos` and `expected_videos`, and bounded failure notes. Complete requires known totals and every file saved. Unknown totals, oversized files, streamed/blob video sources without supported downloads, login restrictions or interrupted galleries remain partial/unavailable. Never substitute a poster or screenshot for a video, mark capture complete after downloading just the lead photo, or claim playback from a thumbnail. Do not reconstruct video streams or bypass access controls. Omit media arrays on later price-only observations to retain saved files; an explicitly complete new capture replaces the saved gallery. File retention does not verify current listing facts.

Facebook's “View photo N”/“View video N” labels can share one mixed gallery index. Keep that label for navigation, but assign saved photo positions `1..photo_count` and saved video positions `1..video_count` independently. A video in gallery slot 1 followed by photos in slots 2–11 means ten photos numbered 1–10 and one video numbered 1 in Goodfinds.

Verify each saved ordinal against its selected source slot. If two slots yield the same content ID, compare their actual loaded sources and readable images: a navigation race can repeat the lead photo, while a seller can genuinely upload the same photo twice. Preserve a confirmed source duplicate and explain it in capture notes. Correct an accidental repeated download by revisiting the affected slots and attaching a complete, ordered capture. Do not deduplicate separate listings solely because they share photos, or remove real gallery slots solely because their bytes match.

The panel serves locally saved videos only after the buyer chooses Load video, with playback controls and no autoplay. It makes no live marketplace media requests. Collection failures remain in the saved evidence; they do not justify fabricated replacement media.

## Gallery and seller evidence

For each shortlisted listing in the verification pass, traverse the whole photo and video gallery, including media below the fold or behind navigation controls. Inspect photos at readable size and play seller videos through their supported controls. Record `image_review.total_images`, the unique image ordinals in `reviewed_positions`, and `complete` only after every image is reviewed. Image ordinals count photos only. Separately record `video_review.total_videos`, unique `reviewed_positions`, `complete` and optional `notes`. A complete video review requires viewing every available clip; an inaccessible or partly played clip remains incomplete. A video thumbnail is not a product photo or a watched video. Capture conflicts and unreadable areas in the notes. Each cached photo has its ordinal and a useful caption describing observed evidence.

Look for device information screens, product labels, model or part numbers, capacity markings, dimensions, included accessories and physical defects. Apply this to any product category. Transcribe readable facts and reference the image ordinal in `evidence`; avoid filling gaps from a title, appearance or common configuration. Save visibly included essentials in `attributes.accessories` and their photo references in `evidence.accessories`, or update the matching `verification_checks` to confirmed. Reconcile those findings with the checklist before preparing seller questions. A visible portafilter, basket or tamper resolves its inclusion question; it does not prove functionality. An operational screen can show that a device powered on but does not prove every function works.

When a readable public model identifier could resolve a required detail, search that exact identifier and open the manufacturer's specification or model-identification page. Record the identifier, source image, source URL, supported facts and remaining ambiguity. A family model number may cover several configurable memory/storage options; only an exact code that uniquely identifies the sold configuration establishes those capacities. Keep serial numbers out of external lookups. If text, packaging, photos or a shop screenshot disagree, keep the advertised device's affected specification unknown until resolved.

Save the actual browser-observed image files, rather than preview-page screenshots or guessed CDN URLs. `downloadMedia` works on supported media elements. If the avatar is rendered as an SVG image, use the browser's observed page-assets inventory and export that specific image asset. Cache downloaded photo/video paths with `cache_goodfinds_media` and avatar paths with `cache_goodfinds_images` in batches within their reported limits. Attach returned IDs through `photos`, `videos` and `seller_avatar_media_id` in `import_goodfinds_listing_observations`. Image bytes stay in the shared local data directory outside the plugin; the panel loads them separately and does not make Facebook image requests. Record download failures without fabricating replacement photos.

For the seller, record only visible account metadata: Facebook join date or year, whether a custom profile image is present, excerpts and check time. Do not collect last-active information. A default silhouette does not count as a custom photo. An unavailable photo or hidden date is unknown. A year-only date remains `YYYY`; it does not establish an exact age. Do not substitute the Marketplace join date, listing date or account activity for Facebook account age.

Open the seller’s Marketplace profile and record the number of **current Marketplace listings**, across categories, when shown. Save `seller_listing_count`, original `seller_listing_count_text`, `seller_listing_count_precision`, `seller_listings_checked_at`, the observed `seller_profile_url`, and a source excerpt under `evidence.seller_listing_count`. Use `exact` for an explicitly displayed total or a fully traversed, uniquely counted current-listings section. Count the candidate when it is in that section. A partly loaded page gives only a `lower_bound`; rounded totals are `approximate`. Do not substitute sold/history counts, followers, reviews or the number of ads matching this search. A hidden or inaccessible total stays null, never zero. Counts may change: filters require a check within 30 days, a source profile and an excerpt. Lower bounds can satisfy a minimum or exceed a maximum, but cannot establish an upper limit; approximate counts stay unverified for hard limits. The panel shows every known reported count and puts source wording, freshness and other profile details in a hover/focus tooltip. A listing count is a search preference, not a credibility guarantee.

Open the listing's seller profile and follow its visible **View profile** link to the Facebook profile. Check the profile header or public Friends section for an aggregate friend total. Record the observed profile URL, display text, numeric count and precision (`exact`, `approximate` or `lower_bound`), source excerpt and profile check time. For example, `1.2K friends` is approximate and `500+ friends` establishes a lower bound. Followers, following and mutual-friend totals are separate metrics. A list of visible names does not establish the total; record the count as unknown when it is hidden or unavailable. Collect the aggregate relevant to this listing, without storing friend names or requesting friendship to expand access. Other visible aggregate seller markers, such as ratings and review counts, can be recorded as labelled context rather than substituted for friends.

## Seller inventory context

When the seller’s current profile shows several goods similar to the candidate, inspect those item pages and save an optional `seller_inventory_review`. Use the candidate’s saved `product` as `category`, a readable plural `category_label` such as `laptops` or `coffee machines`, `item_kind: goods|rental|service`, the exact observed `seller_profile_url` as `source_url`, a timezone-aware `checked_at`, and an `evidence` excerpt describing the inspected group. `listings` contains up to 30 distinct items, each with `listing_id`, canonical same-platform `url`, observed `title`, `availability: active`, and an `evidence` excerpt establishing its item type, seller association and current availability. Complete inspection of a short sample establishes only that sample; keep the overall profile total separate. Leave the review absent when access or evidence is insufficient.

The panel shows **Possible reseller** when a review from the last 30 days contains at least five distinct active goods in the candidate’s category. The tooltip exposes the inspected item links and check time. Show known overall counts directly: `20 listings` for an exact count, `20+ listings` for a lower bound, and `About 20 listings` for an approximation; hide unknown counts. A count already communicates inventory volume, so it needs no additional volume badge. These signals neither establish business status nor change the deal calculation. Total volume does not establish that a seller is moving or reselling, and rental/service inventory does not receive a reseller label. Record an explicit moving sale or negotiability statement as quoted seller context in `seller_profile_notes` rather than inferring it.

Optional seller/profile enrichment happens after the discovery pass and first provisional imports. Use one bounded attempt, then preserve unknown metadata and continue. A required seller-count filter still needs fresh evidence before final eligibility. Download failures do not require repeated retries or delay broad query coverage.

# Credibility check

The prototype's adjustable `credibility_policy` defaults are a 24-month recent-account window, at least 10 other exact-configuration listings, and a price at least 3 sample standard deviations below their median. Candidate and duplicate observations are excluded. The mean still determines a good deal. These checks use observed asking prices and establish neither a statistical probability of fraud nor complete market value.

The separate supporting-profile signal combines an account known to be older than that 24-month window with at least 100 visible friends. The friend threshold is a prototype default configurable as `established_account_minimum_friends`, not a validated authenticity cutoff. Use a fresh profile check, observed profile URL and a friend-count excerpt. Only exact counts or sufficient lower bounds establish this signal; approximate totals remain contextual. Preserve the actual count even below the threshold. Supporting signals are independent of the comparison sample and can appear when pricing data is insufficient. They do not override review flags, change the arithmetic-average rule or trigger repeat alerts by themselves.

When the unusual-price check passes and a recent account or absent custom image is evidenced, keep the listing as `needs_review`, suppress its automatic deal alert and show the reasons. Seller signals are used only when supported by a source excerpt and a check within the past 30 days. If only the join year is known, apply the recency test to the possible date range; a range spanning the cutoff stays unknown. Hidden fields and a small comparison sample remain explicitly unknown or insufficient, rather than becoming reassuring evidence.

If all peer prices are identical, standard deviation is zero and no deviation score is reported. The prototype instead flags a gap of at least 50% below that peer price, still requiring the seller signal. This separate guard is not the threshold for an ordinary below-average deal. The shared tracking layer also records robust median/MAD price flags and long advertised-age flags. Those flags preserve the listing as context; cheapness or age alone does not establish a scam or an unremoved sold ad. Compare full outright asking prices regardless of accepted payment method, excluding finance instalments and deposits. The existing combined seller/price review excludes affected observations from price baselines and alerts while retaining their history.

A new account alone, an absent avatar alone or a small normal discount does not trigger this combined flag. Re-evaluate after evidence changes and withdraw pending alerts when a listing no longer qualifies.
